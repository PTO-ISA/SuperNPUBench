# 为什么这颗 ELF 值得归档（机制摘要）

完整推导、假设清单与失败尝试在模型仓的归档里（`LinxISA/SuperScalarModel` PR #1240 →
`archives/ndf-algod2-20261110-r1/analysis/`）。这里只保留与"这颗 ELF 的测量值怎么读"直接相关的部分。

## 现象

同一颗 ELF、同一份入口配置，只改 tile 绑定与 VEC_IQ 深度：

| 配置 | 拍数 |
|---|---:|
| eager, `vecL1Depth=32`（本包主例） | 143,883 |
| eager, `vecL1Depth=128`（修好准入后） | 143,838 |
| lazy, `vecL1Depth=128`（修好准入前） | 165,091 |
| eager, `vecL1Depth=32`（未含 #1182） | 144,036 |

变慢的那一臂里，被观察块等拆分槽 117 拍 vs 对照 194 拍，而 FMA lane 空闲率约 92%；同一次对比中 CellReg 读队列近空（0.6/9 槽）、tile 绑定失败为 0。

## 机制

VEC 的 tile-op 拆分器只有 4 个槽，修复前按程序序先进先出，且三类（INT/FMA/LNEXP）共用。一个大的 INT tile op 排在前面时会把 4 个槽全部占住，FMA 侧即使就绪也只能等——这就是"队列加深反而更慢"的来源。

修复（PR #1182）改成类感知准入：空槽优先接纳"当前没有在槽 tile 的类"里最老的候选，队首等待超龄后旁路，每类槽数上限 ⌈N/2⌉。修复后深队列与浅队列落到同一量级（143,838 / 143,883，差 45 拍）。

## 怎么读本包的数字

- **143,883 是"这颗 ELF 在冻结探索配置下"的值**，不是这颗 ELF 的最优值，也不是对主线的收益。
- 同一份入口配置在**未改动的主线**上是 143,749，比本分支快 134 拍。两臂还差 33 个主线提交、8 个分支提交和两个语义旋钮（resident tag 36 vs 被夹到 8；类感知准入 vs FIFO），所以**不做归因**。
- 与 `fa-scoped-packed-rowsum-20261109` 里 `fa-64k-unscoped-d2-258099` 的 258,099 是**同 ELF、不同模型（asl `bdbafed5`）与不同配置**，不可相减。
- 所有数字都是零输入计时；日志只有运行完成证据，没有数值比对。

## 失败尝试（同上，摘要）

- 只加宽拆分带宽（`vecSplitBandwidth=8`）：修复前后都不解决头阻，收益在噪声内。
- 把 lazy 绑定当默认：修好后与 eager 同量级，但要额外两处修复（#1204、#1218）才不 abort。
- 单看 CellReg 容量/带宽、tile 绑定延迟、拆分器服务能力：三项都被实测排除。
