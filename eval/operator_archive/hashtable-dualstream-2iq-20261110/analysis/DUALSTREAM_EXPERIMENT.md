# 双流实验记录（hashtable 拆两半）

日期：2026-11-04
目标：把 6144 个 key 拆成两个 ELF，在 `feat/dualstream` 模型上同时跑，看能否填掉 VEC 气泡。
结论：**没测到双流拍数——两条 vector 流在模型上确定性死锁**（约 17.3k 拍），且与我们的拆分无关。

## 3. 双流：确定性死锁

| 实验 | 结果 |
|---|---|
| `-f htA --elf2 htB0 --conf dualstream` | `Deadlock detected at thread 0, cycles=17254, verified blocks=40` |
| 同上但 `-s cell.tile_reg_size=1024`（tile 寄存器 ×4） | **同一拍 17,254 死锁** |
| 同上但 `-s bctrl.vecIssueQDepth=256`（VEC_IQ 深度 ×4） | **同一拍 17,254 死锁** |
| **T=8 单镜像诊断**：`-f htA --conf dualstream`（同一份 ELF 喂两个域） | **也死锁**，cycles=17,367 ⇒ **与"拆两个 ELF"无关，是模型两条 vector 流本身** |

**死锁拍点与三个容量参数全部无关（都是 17,254）⇒ 逻辑死锁（依赖成环），不是容量不足。** 容量不足只会把卡点往后推，不会落在同一拍。

日志证据：
- 8 个上下文都在跑（STID0–7 都有 BCC.STAGE 活动），不是 B 流没启动。
- 死锁时 PE0/STID0 有 **141 个块在飞**（commitPtr 38 / allocPtr 179），其中 B38 `TMUL rdy:1`、B39 `TCI rdy:1`、B40 `TSEL rdy:1` 都已就绪但**没有执行**；B41 `MGATHER_MASK rdy:0` 在等 B40 的输出 tile。
- 即"就绪但发不出去"，不是等数据。

## 4. 修复后重跑结果（2026-11-04 晚）

另一个窗口的修复：`VecTopOf(stid, vecTopCount)`——VecTop 是每 PE 一个引擎，双流下 stid0 与 stid4 都落在 VecTop 0，之前用裸 stid 索引会访问不存在的 VecTop 4–7，**把第二流的 cell-ready 唤醒全丢了**。改动文件：`ModelCommon.h` / `BIssue.cpp` / `VecTop.cpp`（worktree 内未提交改动）。

| 组 | Total Cycles | 说明 |
|---|---:|---|
| 完整 6144，单流（`--conf fourpe`） | **135,299** | 修复后仍逐拍不变 ⇒ 单流 no-op 成立 |
| 半 A（前 3072），单流 | 67,847 | PASS |
| 半 B（后 3072），单流 | 74,112 | PASS |
| **双流 A+B** | **144,826** | finisher 0x5555 PASS，无死锁 |
| 双流 B+A（互换校验） | 143,128 | PASS ⇒ 两半都算对 |

**结论：双流比单流整跑慢 7.0%，这个方案在本模型上不成立。**

### 为什么反而更慢

| 指标 | 单流 | 双流 |
|---|---|---|
| kernel span | 73,223 | ≈78,950（+7.8%） |
| 每轮 gather 间隔（中位） | **450**（四个 PE 全一致，p10=67） | **534–827**（PE5 最好 452，PE0 最差 827） |
| gather 平均时长 | 250–290 | **295–480** |
| VEC 块占用并集 | 62.5 / 61.3 / 72.8 / 66.7 % | **49 / 71 / 65 / 49 %**（没有上升） |
| VEC_IQ 深度 64→128→256 | — | **144,826 / 144,826 / 144,826**（逐拍相同，说明队列从未满） |

两条流的工作总量不变（gather 总数都是 700），但：

1. **每轮的依赖链被拉长**（450 → 534–827），根因是 8 个上下文共享同一个 TLSU/仲裁，**单笔 gather 的排队时间涨了**（250–290 → 295–480）。
2. **VEC 引擎并没有被"填满"**——占用率反而下降。之前 62–73% 那个数字是"块生命周期并集"（含等待），不是可用吞吐；**真正的瓶颈是每轮串行的依赖链，不是引擎闲着**。
3. 所以两个同相位负载并行时不是互补，而是**互相加长对方的等待**：省下的是零，付掉的是仲裁税。

### 对之前预估的修正

先前基于"VEC 占用 72.8% ⇒ 上限 1.37×"的估算**作废**。那个 72.8% 不能读出"还有 27% 可用吞吐"。实测是同等工作量下 +7.0%。

### 若要继续这条路

真正的杠杆不是拆流，而是**缩短每轮依赖链**（同 [[ANALYSIS.md]] 第 4 节）：减少每轮的 mask 操作（12 个 TSEL/轮）、把 `anyActive` 归约降到每 N 轮一次、或者让多条 lane 组的探测彼此独立（同一线程内多条 query 交错，而不是靠第二条流）。

### 相位锁的验证（2026-11-04 追加）

VEC 块在两个流之间确实交替推进：56,780 个 VEC 块中，相邻块"换流"占 **49.7%**，run 长度中位 1（只有启动阶段出现长串，最长 891）。即两流以约 1:1 的速度前进，节拍锁死。

人为错开 B 流启动（在 `main()` 开头加 volatile 空转循环）：

| 配置 | Total Cycles | 相对 144,826 |
|---|---:|---|
| 无延迟 | 144,826 | — |
| B 延迟 150 次循环（≈0.6 个轮周期） | **141,524** | **−2.3%** |
| B 延迟 400 次循环 | 142,996 | −1.3% |

⇒ 相位锁确实是成本之一（≈2–3%），但错开有最优值，且错开后仍然 **141.5k > 单流 135.3k**。

### 拆分槽（PR #1182 机制）的影响

| 配置 | 单流（完整 6144） | 双流 |
|---|---:|---:|
| `vecSplitBandwidth=4`（默认） | **135,299** | 144,826 |
| `=8` | 136,452（+0.85%） | **141,460（−2.3%）** |
| `=16` | — | 141,850 |

方向相反（加深拆分池对单流有害、对双流有利）⇒ 双流确实在共享的 4 个拆分槽上互相头阻，贡献 ≈2–3%。PR #1182 修的是同一族问题（跨 pipe 类头阻），但需要额外补"流维度"才适用。

### 结论（决定性）

- 相位锁：≈2–3%；拆分槽头阻：≈2–3%；其余 ≈4.5% 是 gather 排队与依赖链拉长。
- 三者叠加也回不到 135,299 —— **"填 VEC 气泡"没有可用容量**：两条流共享同一个 VecTop/TLSU，本质是各降一半速率。
- 之前基于"VEC 占用 72.8% ⇒ 1.37×"的预估**彻底作废**。

## 5. 结论

- 双流的**单流路径**是好的（135,299 逐拍复现），拆分与校验也正确。
- **两条 vector 流并发时模型不前进**，因此本实验测不到 `D`，也无法验证"VEC 气泡能否被填掉"的 1.35× 上限。
- 该现象与归档文档里 v1 的"一条 Vector + 一条 CUBE"边界一致；issue #1137 虽已把"两流都可跑 VEC/CUBE"放开（VEC_IQ 单队列共享、CellReg 每 PE 共享），但**两条纯 vector 负载仍会卡住**。

## 5. 建议的下一步（按优先级）

1. **定位 17,253 处的卡点**：B38/B39/B40 就绪但未发射 ⇒ 看 PE0 的 VEC_IQ 里是否有来自 STID4 的块占住队头、或者 VEC_IQ 的 `FullFor` 对两个 stid 的配额判断有误。
2. **对比 vec+cube 的正常组合**：用归档里那颗 `tmatmul_*` 当第二流，确认共享 VEC_IQ 在"只有一条 vector 流"时正常，从而把范围收窄到"两个 stid 同时发 VEC 块"。
3. 若确认是 VEC_IQ 的跨流公平/队头问题，再回来跑本实验——`D` 的判据不变（`D ≤ 0.85 × 135,299`）。

## 7. 结论修正：双 VEC_IQ + 等容量才是正解（issue #1206）

第 4 节的"双流比单流慢 7%、没有可用吞吐"是在**共享 VEC_IQ**下得到的。恢复"每 (stream, PE) 一条 VEC_IQ"（`git apply -R <(git show b04f3ae50)`）并把每分区深度减半保持总容量后，结论反转：

| 配置 | Total Cycles | 校验 |
|---|---:|---|
| 单流完整 6144（`--conf fourpe`） | 135,299 | PASS |
| 双流 · 共享 VEC_IQ（4×32=128 格） | 144,826 | PASS |
| 双流 · 共享 VEC_IQ，A/B 互换 | 143,128 | PASS |
| **双流 · 每(stream,PE) VEC_IQ（8×16=128 格）** | **134,596** | **PASS** |
| 双流 · 同上，A/B 互换 | 137,688 | PASS |
| 双流 · 每(stream,PE) VEC_IQ，深度 32（8×32=256 格） | >1,300,000（kill） | 病态 |

- **净收益**：相对共享队列 −7.1%；相对单流整跑约打平（−0.5%）。
- **病态变慢的锅不在"分区"，在深度没减半**（总容量 128→256）。同样补丁 `vecL1Depth=16` 正常、`=32` 跑到 130 万拍。
- 之前"地板 = 两份半跑之和 141,959"的推断作废——去掉跨流队头阻塞后能跑进它以内。
- 待查：8×32 为何病态（VecTop 侧每拍收两个块 + 4 个拆分槽的交互）；`seg2` 统计槽位在 8 分区下与 TMA/TAU 撞号且越界（`BIssue.cpp` seg2Iq 映射、`bctrl_stats.h` 的 `kCtlStack2IqCount=7`）。
